# RAG Node

The **RAG Node** (Retrieval-Augmented Generation) ingests documents into a [Weaviate](https://weaviate.io) vector database and retrieves the most semantically relevant chunks to use as context for an [AI Data Processing Node](/docs/nodes/ai/llm-process).

![RAG Node](/img/nodes/rag-node-preview.webp)

It connects exclusively to the **AI Data Processing Node** via a dedicated RAG port (right side of the node).

## Prerequisites

- A running Weaviate instance that Agentic Signal can reach. For a an example of installation, see the [Weaviate Setup](/docs/getting-started/weaviate-setup) guide.
- Weaviate should be configured for external embedding input, typically with `DEFAULT_VECTORIZER_MODULE=none`.
- If your Weaviate instance requires authentication, provide the credentials using the node's `API Key (optional)` field.
- A working Ollama host if you are using an Ollama embedding model in the node.

## Inputs

The node receives its input from the connected [AI Data Processing Node](/docs/nodes/ai/llm-process). That node forwards the text it receives from a [Data Source Node](/docs/nodes/input/data-source) or any other upstream node, formatted as markdown with optional file blocks and a query:

````
Using the attached document, answer:

What are the main topics covered?

### File name "my-document.txt"
```
<file content here>
```
````

- **File blocks** (optional): One or more `### File name "..."` sections, each with the file in a code block, as the Data Source writes them — each is chunked, embedded, and stored in the collection. A document is taken whole, its own headings and code blocks included.
- **Query** (required for retrieval): The text preceding the first file or image block. Used to perform a vector similarity search against the stored chunks.

Only text files reach the node: in the Data Source, a file set to **Included in LLM context**. Files set to **Passed to tools only** (PDF, DOCX and other binary files by default) go to tool nodes, not to the RAG node, and images aren't stored either.

If no files are provided, the node performs a query-only retrieval against the existing collection — useful for interrogating a database populated by other workflows or external tools.

## Outputs

The node outputs the most relevant text chunks as a formatted context string, injected into the [AI Data Processing Node](/docs/nodes/ai/llm-process)'s prompt:

```
[1] (my-document.txt)
...chunk content...

[2] (my-document.txt)
...chunk content...
```

If no relevant chunks are found, the output is empty (`null` context) and the AI node proceeds without RAG context.

**The AI node doesn't get the files themselves.** With a RAG node connected, it reads the chunks, then the message without its text files: the question, any images, and the User Message prefix and suffix. So a document doesn't fill the model's context window, however long it is; the model sees only the parts that answer the question. This holds in orchestration mode too: the RAG node is asked once, and the agents plan from what it found and the question. A run that sends files without a question still asks the model, with whatever is left of the message: write the request in the Data Source along with the files.

## Ingestion Lifecycle

The node uses **per-file content hashing** to avoid redundant re-embedding:

<div className="fullWidthTable">

    | Scenario | Behavior |
    |---|---|
    | File is new to the collection | Embedded and inserted |
    | File content unchanged | Skipped — existing vectors reused |
    | File content changed | Old chunks for that file deleted, file re-embedded and re-inserted |
    | File removed from workflow input | Chunks remain in DB — preserved for other workflows |
    | Embedding model changed | Entire chunks class dropped and all current files re-ingested |
    | Query only (no files in input) | Queries whatever is already in the collection |
    | Query with another embedding model than the collection's | Fails, naming the collection's model |
    | New or changed files, or another model, for a collection made with another owner key | Fails, naming the collection; nothing is written |

</div>

This makes the node safe to use in a **shared knowledge base** scenario: multiple workflows can contribute documents to the same collection without overwriting each other's data.

## Owner Key and Deleting Collections

A collection made by a node with an [owner key](#configuration) belongs to that key. Weaviate keeps only the key's fingerprint (a SHA-256 hash), never the key itself.

<div className="fullWidthTable">

    | | Query | Add or replace files, change the model, delete |
    |---|---|---|
    | Collection made without an owner key (every collection made before owner keys existed) | Everyone | Everyone |
    | Collection made with an owner key | Everyone | Only nodes with that key |

</div>

**Deleting:** in the collection list (🔍), a bin appears next to each collection this node may delete, and Agentic Signal asks you to confirm first. The collection's chunks and file list are removed from Weaviate; this can't be undone. Only collections Agentic Signal made can be deleted this way: a class without a meta class (made by another tool) has to be deleted in Weaviate.

**Sharing:** to let colleagues maintain a collection, share its owner key with them, as you would a password. People who only ask questions don't need it.

:::warning What an owner key doesn't do
It guards against accidents in Agentic Signal, such as one team wiping another team's collection. It isn't access control: anyone who has the Weaviate API key can still change or delete any collection directly in Weaviate. To control who can read or change what, and to know who did it, use Weaviate's own users and roles, and back the data up regularly: see [Weaviate Setup](../../getting-started/weaviate-setup#sharing-weaviate-roles-audit-logs-and-backups).
:::

## Weaviate Schema

Each collection is stored as two Weaviate classes. The class name is derived from the collection name by stripping non-alphanumeric characters and uppercasing the first letter (e.g. `rag_collection` → `Ragcollection`; `Rag` goes before a leading digit, as in `2024 notes` → `Rag2024notes`). So names that differ only in punctuation (`my-docs`, `my_docs`) are one collection.

**Chunks class** (`{ClassName}`, e.g. `Ragcollection`):

```json
{
"class": "Ragcollection",
"vectorizer": "none",
"properties": [
    { "name": "content",    "dataType": ["text"] },
    { "name": "sourceFile", "dataType": ["text"] },
    { "name": "chunkIndex", "dataType": ["int"]  }
]
}
```

Each object also carries a `vector` (float array). Dimension depends on the embedding model — `nomic-embed-text:latest` produces 768-dimensional vectors.

**Meta class** (`{ClassName}Meta`, e.g. `RagcollectionMeta`):

```json
{
"class": "RagcollectionMeta",
"vectorizer": "none",
"properties": [
    { "name": "documentHash",   "dataType": ["text"] },
    { "name": "embeddingModel", "dataType": ["text"] },
    { "name": "originalName",   "dataType": ["text"] },
    { "name": "ownerKeyHash",   "dataType": ["text"] }
]
}
```

Exactly **one object** exists in the meta class per collection. `documentHash` is a JSON map of `{ "filename": "sha256hex", ... }` for per-file change detection. `originalName` stores the human-readable collection name (e.g. `rag_collection`) for display in the UI. `ownerKeyHash` is the owner key's fingerprint, set once when a node with an owner key creates the collection; meta classes made before owner keys existed don't have it, and their collections stay open to everyone.

**Minimum viable external collection** (to be queryable from Agentic Signal without triggering re-ingestion):
1. Create `Ragcollection` with `content`, `sourceFile`, `chunkIndex` properties and correctly-dimensioned vectors.
2. Create `RagcollectionMeta` with one object: `{ documentHash: "{}", embeddingModel: "nomic-embed-text:latest", originalName: "rag_collection" }`.
